# 协议建号复核：先校验实验，再判断失败原因

核对日期：2026-11-15。审查对象：`tools/signup`、本地脱敏回执和协议 A 指纹配置契约。本轮只执行本地测试及官方文档查询，未向 Apple 发起注册、发码、登录或指纹采集，未调用付费供应商。

## 结论

**当前证据不足以认定 `-34607001` 仅由 TLS/JA4 或出口信誉导致，也不足以排除协议实现和环境一致性问题。** “验证码错误消失”只表示返回了不同的拒绝结果，不能证明其余字段和所有后续步骤均被接受。

协议 A 最值得借鉴的是：配置有单一来源、实际引擎可核对、同任务保持一致、恢复需有完整会话材料、证据不足时停止。浏览器家族比例、版本模板和伪装参数不应直接搬到 Apple；其契约本身也不保证服务端接受。

## 已复现并修复的缺陷

| 问题 | 影响 | 本轮修改与验证 |
|---|---|---|
| 构造函数丢弃 UseCurl/SkipLanding/CHHints/HTTP2 和 curl 的代理地址 | 参数看似切换，实际仍走 Go；跳过落地页未生效；原传输对照无效 | 显式赋值；构造测试与本地 HTTP 请求计数验证 |
| Go HTTP/2 开关未设置 ForceAttemptHTTP2 | 自定义 Transport 不等于实际启用 HTTP/2 | 显式配置；回执只声称 requested，不冒充已协商协议 |
| curl 用 `fmt.Sscanf("HTTP/%*s %d")` 解析状态 | Go 不支持这里的 C scanf 跳过写法，正常 200 也解析失败 | 按状态行字段解析，测试 HTTP/1.1、HTTP/2 及代理 CONNECT 多段头 |
| curl 忽略 HTTP 版本/超时选项，同进程 Session 共用按 PID 命名的 cookie 文件 | 对照条件不可信，会话可能交叉污染 | 显式传递版本和超时，每个 Session 独立临时 jar；本地 curl 往返与 cookie 测试 |
| 默认 UA 是 Chrome 141，Client Hints 写死为 157；新采 FD 的 U 也是 157 | 三个来源矛盾；原有 Hints 开关未生效，所以不能声称旧请求实际发送过它 | Hints 使用配置中的 Chrome 主版本；FD JSON 的 U/L 必须匹配 UA/locale，否则网络请求前拒绝。检查不覆盖完整 FD、时区、硬件或 TLS 等价性 |
| 仅凭 HTTP 2xx 判断成功 | `hasError`/错误数组可能被误判为成功 | 检查业务错误标记，离线 200 错误回包测试 |
| 任意 4xx 后自动换 contactEmail 端点再发/交验证码 | 423 等拒绝也会触发第二次操作，混淆实验且不符合停止规则 | 去掉跨业务分支的自动回退，验证 423 只请求一次 |
| attempt 脚本硬编码供应商及代理凭据，默认价格且直接购买 | 与用户“价格另议、默认不扣费”冲突 | 移除凭据；供应商/识别密钥从环境读取，代理显式配置；默认无价格，购买须显式 AllowPurchase 和正数 MaxPrice |
| 脚本只解析 JSON，不核对子进程退出码 | 失败进程可能被当作阶段完成 | 非零退出码明确归入失败 |

本机 `curl.exe --version` 显示 Schannel，Features 未包含 HTTP2。原注释“curl 使用 OpenSSL”不符合本机事实；更不能据此把系统 curl 视为 Chrome。`--http2` 在不支持的运行库上失败应保留失败，不能静默换引擎。参考 [curl TLS 后端说明](https://curl.se/docs/ssl-compared.html) 与 [curl 参数文档](https://curl.se/docs/manpage.html)。

移除当前源码中的凭据不清除 Git 历史。此前暴露的供应商、识别服务和代理凭据需要由所有者轮换；本轮没有改写仓库历史或操作供应商密钥。

## 浏览器对照 r5：可证明什么

本地私密证据：`.cache/r5/run.jsonl` 与 `profile.json`。不提交原记录、账号、号码、OTP 或认证材料。

- 日志时间为北京时间 2026-11-13 21:19:33.864 至 21:21:19.737，约 105.9 秒。
- 记录了 captcha 201、邮箱可用性 200、密码检查 204，以及 **`POST /account/validate` 200**，随后进入 email_step 和 phone_step。
- 最后一次 phone_step 用时 1258ms；但最终有 `locator.count: Frame was detached` 和 `state=failed`。这属于自动化观察失败，既不能直接证明账号未建成，也不能当作最终成功回执。
- 保存的配置写的是 Windows/Chrome 154、en-US、America/Denver。应区分配置档案与实际浏览器观测，不能把“系统默认”当作已核实配置。
- 用户补充：当时使用 QQ 邮箱、英国号码、美国住宅粘性出口；后续正确密码登录遇到 2FA。后续登录原始证据尚未在本次提供的路径中核对，因此单独记为用户报告。

该样本是有效的 **validate 已通过** 基线。若所述跨国配置无误，则“出口国必须等于号码国”不能作为普遍必要条件。一次通过也不能证明 QQ 域、逐字符输入、105 秒耗时或一次图形码就是成功原因。

`capture6/network.jsonl` 被旧说明称为完整建号抓包，但本次统计仅见 validate 400，没有邮箱/短信验证成功链。近期 attempts 回执只有三条：引导 404、号码 ExceedsLength、validate -34607001，均无 created/email_verified 成功标记。另三个浏览器对照目录也没有成功结束记录。仅凭这些材料不能声称邮箱码和短信码已被真实服务接受。

## 尚未修复的完整链路问题

这些问题独立于当前 validate 拒绝；不能把修复上述七类请求问题称为纯协议全链路完成。

1. **跨进程会话没有恢复。** main 的每个 stage 都 newSession + Bootstrap；state 只存业务字段，不存 scnt、sessionId、挑战和 cookies。attempt 又为发码、交码分别启动新进程。它不是原注册会话续跑。应先用经核对的成功协议证据明确挑战与会话归属，再选择单进程等码或完整私密会话恢复，不能只补存一个 scnt。
2. **没有安全的阶段重放契约。** create 不检查既有写意图，保存状态失败只警告，且 state 文件缺锁与原子替换。旧文档“同一 stage 幂等”不成立。短信/邮箱发送同样有外部副作用，遇未知结果不能重新发送试探。
3. **成功判据过早。** Created 是 validate 接受标记，`all` 实际止于 validate；used=true 只表示地址已占用，不能独自证明该任务创建并拥有账号。旧 mock 在 validate 时就把 created 设为真，未验证真实终建流程；测试已重命名，避免伪称线上全链路回放。
4. **attempt 仍不是生产编排器。** 号码先买后预检，发邮箱码结果未完整检查，Graph 返回邮箱与本任务缺绑定检查；退款 parked 没有真正 sweep，未知购号结果也没有与既有产线账本统一。新增购买闸门仅防默认扣费，没有使其具备生产恢复能力。继续使用已接入的面板产线管理成本，不应直接替换为此脚本。
5. **完整身份/出口证据不足。** FD 采集工具没有代理入口，关闭独立浏览器后只取部分材料；单独有新鲜 FD 不代表它与协议请求同一会话、出口、浏览器或传输环境。单一端口也不是实际出口 IP 的证据。当前一致性校验并不证明 Apple 接受。

## 下一步取证顺序

先核对 r5 后续登录的脱敏状态与时间，确认业务最终结果；保留账号材料在私密目录。再以已有浏览器成功步骤为参照，对照实际方法/路径、字段 schema、会话归属和终建判据，补齐跨进程边界测试。

只比较已经核实的运行条件，并记录实际引擎、构建版本、配置签名、阶段、HTTP 状态与错误码；不在普通日志放原始响应、Cookie、密码或代理认证地址。控制住代码和会话缺陷后，才能讨论外部拒绝原因。不要以连续换 IP/指纹、反复提交或单个通用错误码替代因果证据。

## 本轮验证

新增七项测试先在旧实现失败，再修复通过；另外验证本地 curl HTTP/1.1 往返、同 Session cookie 保持与不同 Session jar 隔离，以及静态购买闸门。`go test ./tools/signup -count=1 -v` 共 18 项，17 通过、1 因 Windows PowerShell 执行策略阻止脚本执行而跳过；未修改执行策略。另做 Go vet 和 PowerShell AST 语法解析。

没有真实注册、购号、验证码服务调用或 TLS 浏览器伪装实验；没有重编译覆盖用户运行中的 signup.exe。当前结果是确定代码缺陷及证据纠偏，**不是已解决 Apple -34607001**。
