# 自建 Outlook 邮箱 → Apple ID（run2，2026-11-14）

目标：用**自己刚注册成功**的 Outlook 邮箱建 1 个 Apple ID，不买付费服务（号码除外）。
邮箱：`D:\outlook-recon\产出\outlook-cn.txt`（单条，`邮箱----密码`，密码不入库、不入日志）。
运行目录：`.cache/apple-run2/`（`.cache/` 已在 `.gitignore`，密码/令牌只落在这里）。

结果：**未建成**。苹果在表单提交第 2 次后给出硬拒绝 `Your account cannot be created at this time`。
号码已按纪律退掉（`ACCESS_CANCEL` → `STATUS_CANCEL`）。取码通道本身已打通（路 B）。

## 1 读信：两条路各自走到了哪

### 路 A：设备码换 refresh_token —— 走不通（微软拦截）

新增 `tools/capture/msa-devicecode.cjs`：设备码 → patchright 驱动本机真 Chrome 走登录 → 轮询 token → 写
`<outdir>/graph.json`（0600）。设备码申请本身成功（`verification_uri=https://www.microsoft.com/link`，`expires_in=900`），
浏览器侧也能输码、能提交密码，但密码通过后微软把流程推进到：

```
https://account.live.com/interrupt/credentialaction?...&id=293577
「帮助保护你的帐户 — 添加电子邮件地址，以便你可在被锁定时安全登录到你的 Microsoft 帐户」
```

排查过并排除的绕行（都在 `--gate-dump` / `--relink` 里实现并实测）：

| 尝试 | 结果 |
|---|---|
| 页面上找「以后再说 / Skip for now / iShowSkip」 | 该模板没有，DOM 里只有 `添加电子邮件` 一个按钮 |
| 回到 `ru=` 回跳地址 | 仍落回同一 interrupt（opid 每次换新） |
| 直接重跑 `microsoft.com/link`（同会话） | 回到「输入你的密码」，说明会话未完成 |
| `Esc` / `#close-button` | 是 banner 关闭按钮，与 interrupt 无关 |
| 用临时邮箱当恢复邮箱（`abc-temp-2026.shop`），逐位填 6 格 OTP | 微软**接受**该域名并发码，码也读到了，但连续两次没打完（见下方教训）后，微软把该账号的**密码登录也关了**：`密码登录不可用。请尝试其他方法。` |

结论：路 A 在「新号无恢复邮箱」这一步被微软按死；继续硬敲只会触发风控（已实测升级为密码登录不可用）。
**token 未拿到，`graph.json` 不存在。**

### 路 B：浏览器登录 outlook.live.com 读信 —— 通

关键发现：上面那道 interrupt **只拦 OAuth 授权，不拦网页收件箱**。
同一会话里 `https://outlook.live.com/mail/0/` 直接进收件箱（截图见 `.cache/apple-run2/shots/inbox-1794593475408.png`）。

新增 `tools/capture/outlook-web-mail.cjs`：持久化 patchright profile → 打开收件箱 → 每 7s 扫一遍
`[role="option"]` 里含 Apple 的行 → 点开 → 从阅读窗取 6 位码 → 写入 `--write` 指定文件（供驱动
`--await-email-code` 消费）。本次运行里它一直活着（收件箱为空时正常空转），是后续可复用的取码通道。

## 2 建号：退出码 / 耗时 / 卡点

| 项 | 值 |
|---|---|
| profile | `go run ./tools/profilegen -dir .cache/apple-run2 -seed apple-run2-ba38c73540` → Chrome 154 / Win32 / en-US / **America/Chicago** |
| 出口 | 本机家宽直连（Clash `mode=direct`），实测 `211.90.236.199` CN 绍兴联通；preflight `ok:true frame:true` |
| 号码 | hero `service=wx&country=16&maxPrice=0.1` → `+44 7849 586202`，单价约 $0.043 |
| 运行 | 共 3 次（前两次被下面两个自身缺陷挡下，每次 ~2–4 分钟），第 3 次在 `--await-captcha` 手工通道下提交 2 次后终止 |
| 退出 | 人工 kill（`Your account cannot be created at this time` 之后继续无意义） |

### 卡点 1：口令不含特殊字符，Continue 一直是灰的（自身缺陷，已修）

苹果表单报 `At least one special character`，`button[type=submit]` 带 `disabled`，
Playwright 点不动 → 日志表现为 `click-timeout`，被误当成验证码不对，白烧了 5 张图。
修：`clickContinue` 的 catch 里补抓 `disabled` + 表单内联错误（`create-account.cjs`）。

### 卡点 2：验证码 OCR 命中率不够（已改增强）

160×70、带噪线的图，YesCaptcha 原图直读经常错（实测把 `DhCBB` 读成 `DHCBR`）。
修：`tools/captcha/solver.py` 增加 `--upscale`（默认 4）：autocontrast + 锐化 + LANCZOS 放大后再送付费识别。
另修：手工通道每轮结束后删答案文件，避免把被拒的答案再提交一次（`create-account.cjs`）。

### 卡点 3：苹果硬拒绝（本次真正的终点）

`--await-captcha` 手工通道下：

* 第 1 次提交（答案 `R4CK7`）：`Please enter the characters you see or hear to continue.` → 验证码被拒；
* 第 2 次提交（答案 `BFDF`，与付费识别两次一致，可信）：页面底部红字
  **`Your account cannot be created at this time.`**，验证码框已被清空 → 这次不是验证码问题，是**建号风控拒绝**。

截图：`.cache/apple-run2/01-submit-1.png`（验证码被拒）、`01-submit-2.png`（苹果硬拒）。

可能相关的一致性缺口（本次 profile 与出口、号码三者不匹配）：

| 维度 | 本次值 |
|---|---|
| 浏览器 profile | en-US / America/Chicago / 1366×768 |
| 出口 IP | 中国 绍兴 联通家宽 |
| 号码 | 英国 +44 |

上一轮（docs/run-20261113d.md）用「住宅代理 + 号码国别」对齐出口，仍撞过 Google/苹果软拒绝；
本轮把出口换成国内家宽后，profile 的 US 时区与 CN 出口直接矛盾，是最可疑的拒绝原因。

## 5 下一轮建议（按性价比排序）

1. **出口与指纹对齐**：profilegen 出的是 US 指纹，就别用 CN 家宽跑苹果；用干净住宅口（DataImpulse 避开
   10013/10030/10033）并把出口国别与号码国别对齐（GB 号 + GB 出口），一致率最高。
2. **号码换国别再试**：本轮 GB 号已在被拒的提交里出现过，复用它意义不大；下一轮按纪律仍只买 1 个。
3. **验证码走手工通道更快**：`--await-captcha` + 人读（本轮 4/5 字符肉眼都准），OCR 只当第二意见。
4. **别再用设备码硬敲微软**：密码登录已被风控关闭，等冷却或直接走路 B 读信。
