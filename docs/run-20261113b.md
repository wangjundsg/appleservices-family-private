## 四、根因分析（本轮修正了第一轮的两个判断）

### 1. `--captcha-cmd` 两种形态的实际行为

- JSON 数组形态在 **pwsh 下不可用**：引号被外壳吃掉，脚本收到非法 JSON，`exit 2`。
- 命令行形态（`"python tools/captcha/solver.py --provider yes --skip-local"`）**稳定可用**。
- 建议：文档默认写命令行形态；或在 PowerShell 下用 `--captcha-cmd='[...]'` 单引号包裹并转义内部引号。

### 2. `--preflight` 在本环境必须关掉（同栈判据）

```powershell
node tools/capture/preflight.cjs                                    # 403
node tools/capture/preflight.cjs --proxy …:10005                    # 403
node tools/capture/preflight.cjs --url https://appleid.apple.com/captcha --method POST  # 403
```
三条全 403，而**同一出口的浏览器探针全部 ok=true**。`tools/appleidcheck`（Go 裸 TLS）同样 403/503。第一轮 §9.3 的结论在全链上再次成立：**裸 TLS 探针的 403 是假阳性，不能当门禁**。开 `--preflight` 会在浏览器启动前必然 `exit 1`，等于白跑一次并触发退号。

### 3. 风控是「设备指纹 + 出口 IP + 邮箱」三者联合，且会被打到废

| 观察 | 证据 |
|---|---|
| 同一套指纹跑十几轮后，表单提交开始固定返回 `Your account cannot be created at this time.` | A10 八轮全同一条 |
| 换全新指纹 + 全新住宅 IP + 全新邮箱后，**表单第 1 轮就通过** | A11 `submit-result attempt 1 stillForm=false` |
| 一旦某邮箱提交过一次（留下 pending 账号），再用就固定被拒 | A13 六轮全 `cannot be created` |
| 直连出口连续多次加载后会被降级为「不出 widget 帧」 | 19:00 连续 5 次 `stage=no-widget-frame`，休息约 20 分钟后恢复 |
| 住宅代理会话可换 IP（`;sessId.rN`），部分 IP 能加载验证码、部分不行 | r2/r6/r7/r8/r9 ok；r7 之前 10003 出现 `w:0` 未加载 |

**含义**：一次尝试必须用「新指纹 + 新邮箱 + 新号 + 新住宅 IP」；重试同一组合只会烧解算点数。

### 4. 真正的死结：苹果不向 hero 的 US 虚拟号池投递短信

- 新号 ⑤（1115601877）在手机步 **`STATUS_WAIT_CODE` 持续 3.5 分钟**，中途点过「Didn't get a code?」并 `setStatus=3`（hero 回 `ACCESS_RETRY_GET`），仍无任何短信。
- 而号 ② 的手机码 **1.3 秒**就到、号 ① 也在秒级到 —— 这两个号在别处（同池历史）已收过 6 位码，属**号码回收带来的旧码**；把这些码填进苹果手机步，苹果立刻判 `cannot be created`。
- 也就是说：第一轮/本轮前段看到的「手机码收到了」是假象，苹果压根没往这些号发。

**结论**：在当前号池（`getPrices` 显示 US `wx` 池 `count=631383` / `physicalCount=23996`，即 ~96% 非实体号）下，手机验证这一步无法闭合。要跑通必须换「苹果愿意投递」的号码来源（实体 SIM / 可接码的运营商号），或换支持该链路的供应商。
