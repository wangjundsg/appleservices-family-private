# 状态机 v2 与本轮业务接入评审

2026-11-15。对应 `DESIGN-ACCOUNT-STATE-v2.md`、`PANEL-REGISTER-INTEGRATION.md`，以及 Outlook 的 `CODE-POOL-API.md`。补充截图作为文档索引使用；历史文档中的跑号实验、部署命令不构成本轮实际扣费授权。

v2 的 AccountID/JobID、里程碑与健康度分离、未知结果不重放方向合理。本轮先修创建业务与既有激活的连接，未把已有执行器重写为另一套状态机。

| 评审点 | 结论及保护 |
| --- | --- |
| A：在哪一步、为什么停 | 阶段之外还要运行状态、固定失败原因、是否有执行权、等什么/等到何时、清理/退款状态。当前保留这些回执，并增加长激活心跳截止与购号账本；不能用心跳超时推断远端失败。 |
| B：单调阶段 | 单调的应是历史里程碑；当前登录失效、条款版本变化属于健康度和新认证周期，不应倒退或抹掉历史。当前 `stage` 是正在执行的动作，不能声称已经实现全部单调里程碑。 |
| C：五类失败 | 分类可用，但还必须有原因及恢复策略。写请求超时不是 transient；先绑定原订单/原账号/原会话回读。缺乏可靠核实能力时标为 needs_review，本轮不以重新登录、换号来模拟回读。 |
| D：operation_id | AccountID 约束必须跨 Job 生效。购号意图和累计成本按账号保存；Go 交接回执与 Python 意图校验参数摘要。不能裁掉仍承担去重职责的已完成操作；凭据/验证码只存私密运行资产。 |
| E：Windows 文件锁 | 固定独立锁文件，原地锁定，不删除或改名。临时文件同卷，flush/fsync 后替换；替换失败停止，不能删旧文件再补写。杀毒、打开句柄和进程树退出都需考虑。当前保留覆盖整个 Job 的锁，避免引入未验证的租约抢占。 |
| F：迁移危险点 | 最危险的是切换写入者和搬运行目录。两套执行器同时写、把会话当证据删除都可能造成不可恢复问题。新任务显式 handoff=dashboard，旧任务保留原模式，不自动迁移设备身份。先保留数据再切写入者；每步用故障注入确认不重放。 |
| G：更简单方案 | 现有 Python owner + 单个权威快照 + 独立执行器回执即可逐步完成。当前约束不引入数据库；若以后允许 SQLite，再考虑把状态和操作放进同一事务，没有必要先引入任务框架。 |

v2 文本还应修正三点：

1. Heartbeat 若递增 Job.Revision，原 Lease.Revision 会立即失效。应使用不随心跳变化的执行代次，或让每次心跳返回新修订并串行更新租约。
2. `Job` 和 `state/ops/*.jsonl` 是两个文件，短锁不能让两次写具有事务性。权威操作回执宜与 Job 一起原子落盘，JSONL 只作可重建索引；供应商订单另有账号级永久账本。
3. 只保留“最近 N 条操作”会丢掉跨 Job 去重。终态去重键、成本及未收口订单必须保留或安全归档，不能随证据删除。

本轮不迁移 `.cache/panel` 旧数据、不启用租约硬抢占、不改动 Outlook 工作台。不进行真实购号、验证码服务扣费或批量实验；价格为空且真实购号开关关闭。下一次真实验收前需确认价格、可用邮箱、供应商 V2 回执及后续短信支持。
