# 新增“产号 provider”对现有并发改造的影响评估（请评估）

> 用途：把即将接入的新组件讲清楚，请正在做并发优化的同学评估——这会不会影响你正在改的队列/准入/后台线程设计，以及需要提前预留什么。

---

## 0. 需求规模（先看这个，决定要不要紧张）

**不是产能型需求。**

- 目标：**12~15 个长期使用的 iCloud 账号**（2 个家庭组，每组 1 组织者 + 5 成员）
- 形态：**一次性建一批，之后每月补 1~2 个**（账号被风控/失效时替换）
- 单次批量：6 个号左右，几天内跑完，之后长期零负载

所以 **并发不是主要议题**：产号侧只需要一条**独立车道**、不阻塞主链路即可，
不需要为它做复杂的资源调度。

长期真正占资源的是**保活**（会话续期、家庭组状态回读），那是低频定时任务，不是并发任务。

---

## 1. 新组件是什么

一个**独立的产号服务**（不是 gpt-free-service 的模块），职责是把「Apple ID 从无到可用」整条链跑完：

```
建 Apple ID（网页创建：表单 → 图灵码 → 邮箱码 → 短信码）
  → GSA 登录（密码 + 2FA）
  → iCloud 网页会话（AuthKit iframe 登录）
  → 同意 iCloud 条款（getTerms → repairDone）
  → 拿 mmeAuthToken（delegate 通过）
  → 开 iCloud+ 50GB
  → 建家庭组 / 拉成员
  → 生成隐藏地址（HME）
```

产物：可用的 Apple ID + iCloud 会话 + 家庭组关系 + 隐藏地址清单。

**定位**：它是 `gpt-free-service` 的一个**注册 provider**，与现有 `roxy` 驱动并列，不是替代。

## 3. 与邮箱池（8788，iCloud-Privacy-Mail-v2）的契约

池子只做**台账**，不执行 Apple 侧动作：

| 动作 | 谁发起 | 谁执行 |
| --- | --- | --- |
| 建隐藏地址 | 产号侧 | **产号侧调 Apple 接口**，成功后 `POST /api/v1/mailbox-pool/import` |
| 改状态 | 产号侧 | `POST /status` |
| 退役/删除 | 产号侧判定 | **产号侧执行 Apple 删除**，再 `POST /retire` 记账 |

理由：只有产号侧持有该账号的 iCloud 会话，池子无法删除真实别名。

## 4. 资源画像（评估并发用）

### 4.1 单任务耗时

| 阶段 | 典型耗时 | 说明 |
| --- | --- | --- |
| 建号（表单 + 图灵码 + 邮箱码 + 短信码） | 3~6 min | 图灵码 OCR 平均 2~4 次尝试 |
| GSA 登录 + 2FA | 1~2 min | 等短信 |
| iCloud 网页会话 + 条款 | 1~3 min | 含等待 |
| 开 iCloud+ | <1 min | |
| 建家庭组 + 拉成员 | 1~2 min | |
| **单号合计** | **6~13 min** | 其中 **60%+ 是外部等待**（验证码/短信/页面） |

### 4.2 每任务独占资源

| 资源 | 数量 | 硬约束 |
| --- | --- | --- |
| 浏览器实例 | 0~1 | **建号阶段用本地 Chrome（Playwright 自启，独立进程，不碰 Forge 50100）**；登录/条款走协议后无需浏览器 |
| 住宅代理粘性会话 | 1 | 一号一 IP，出口国 = US |
| 接码号码 | 1~2 | 单价 $0.13/号，平台库存有限 |
| 临时邮箱地址 | 1 | 自建域名，可无限建 |

### 4.3 外部限流（决定并发上限的是这个，不是 CPU）

- **Apple 按「出口 IP + 浏览器指纹」限流**：同一组合连续创建约 2 个号后，第 3 个开始返回
  `cannot be created at this time`（实测：同 IP 同指纹建 2 个成功、第 3 个被拒；
  换住宅 IP + 换指纹后第 4 个立即成功）。
  **这是按组合计量的**，所以产线采用「一号一 IP 一指纹」，不受该阈值限制；
  真正的产能上限是代理会话数与号码成本，不是这个数字
- 接码平台库存/单价波动
- 代理并发会话数有限

**结论：产号侧天然是「低并发 + 长任务」**，建议 4~8 路；不是靠加线程能提产的场景。

## 5. 与现有系统的冲突点（重点请评估）

0. **前提对齐**：现网主链路是**协议引擎 A**（纯协议、不开浏览器），Roxy/Forge 只是备用通道。
   所以 50100 不是主战场，真正共享的是下面第 1 条的出口 IP。

1. **共享出口 IP 池（最需要定的一条）**
   协议引擎 A 做注册同样要出口 IP；产号侧是一号一 IP（美区住宅，粘性会话）。
   → 两边会不会抢同一批代理？建议把「注册类出口」和「产号类出口」**分池**，
     或给产号侧预留固定的并发会话数，避免互相挤占。

1b. **Forge 50100（次要）**
   仅当 Roxy 通道启用时才开窗；产号侧若也走 Roxy，会有内存竞争。
   → 需要时再加统一并发闸门，优先级低于第 1 条。

2. **长任务占 worker**
   一个 6~13 分钟的任务如果占用通用 worker，会把短任务堵死。
   → 是否应做**按 provider 分池**（长任务池 / 短任务池），而不是共用线程池？

3. **准入控制与「待收尾数量」门槛**
   你现在的准入会检查全局待收尾数量，达到门槛就不派发。
   → 产号侧是否需要**独立的类目配额**（例如：产号任务不占用收尾名额，单独计），否则产号一批会把准入门槛顶满，反而压制其他任务。

4. **后台线程无上限**
   你提到后台线程没有上限，可能增加数据库和内存竞争。
   → 产号侧回写（job 状态、账号结果）是低频写入（每号几次），但如果和其他后台任务共用连接池，是否需要单独的 DB 连接预算？

5. **超时/租约**
   长任务必须有 lease + 心跳，否则会被误判死任务重复派发。
   → 现有队列是否支持「provider 自定义超时（≥15 min）」？还是统一超时？

6. **重试预算与成本**
   每个号有真实成本（号码 $0.13 + 代理流量），不能无限重试。
   → 建议 provider 级重试预算：**每号最多 2 次**，失败即回收，不进入通用无限重试。

## 8. 一句话总结

> 新组件是**外部资源受限的长任务 provider**（4~8 路，单任务 6~13 分钟，60% 时间在等外部验证码），
> 与现有短任务共用同一个 Forge 50100 和同一套准入逻辑时，最可能出现的不是 CPU 打满，而是
> **长任务占住 worker + 准入名额被顶满**——但只在「一次性建 6 个号」那半天发生，规模很小。
> 出口 IP 池与 Forge 50100 都**不构成冲突**（需求量只有十几个号，且产线不开 Forge）。
>
> 请在优化并发时预留「独立 provider 车道 / 独立准入配额」两处扩展点即可，其余保持现状。
