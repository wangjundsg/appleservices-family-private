# 自动化流水线：现状、待解问题与代码评审请求

> 说明：本文描述的是一条**本地自动化流水线**的工程问题（表单自动化 + 身份激活 + 资源导入）。
> 文中用中性词替代具体服务名，便于外部评审聚焦工程本身。
> 评审目标有两个：① 图像挑战识别率的可行解法；② 全流程代码的设计缺陷。

---

## 1. 流水线做什么

```
① 创建账号（浏览器自动化填写表单 + 图像挑战 + 邮箱验证码 + 短信验证码）
② 登录并取得会话（协议实现，含二次验证）
③ 激活云端身份（网页会话 + 条款确认，产出 cookie 集）
④ 登记设备身份（拿推送令牌，向服务端登记本机为一个可信终端）
⑤ 会话保活（定期校验并刷新）
⑥ 生成别名地址（隐藏转发地址）并导入资源池
```

代码位置：

| 阶段 | 路径 |
| --- | --- |
| ① 创建 | `tools/capture/create-account.cjs`、`tools/captcha/ocr.py` |
| ② 登录 | `tools/capture/gsa-login.cjs` + 外部协议实现 |
| ③ 激活 | 外部协议实现（CLI 封装） |
| ④ 设备登记 | `bin/trusted-device.exe`（`cmd/trusted-device`） |
| ⑤ 保活 | `bin/applekeepalive.exe`、`tools/keepalive-all.ps1` |
| ⑥ 别名 + 导入 | `icloud/hme.go`、`tools/hmecli`、`tools/poolimport` |

## 2. 当前卡点（按严重程度）

### P1 图像挑战识别率不足

- 服务端返回的是一张 **126×56 的扭曲字符图**（4~5 个字符）。
- 现用离线 OCR（`ddddocr` beta 模型），实测识别率约 **20%**。
- 流水线做法是"错了就换图重试"，单次成本约 15 秒；16 次上限经常跑满仍不过。
- 已排除的干扰：截图元素抓错（页面里另有一个图标）、失败后未换图、OCR 输出过短仍提交。

**想请评审的问题：**

1. 这类小尺寸扭曲字符图，是否有比 ddddocr 更合适的离线模型或预处理方式（超分、去噪、字符切分后再分类）？
2. 是否值得引入"双模型交叉投票"（两个不同模型都给同一答案才提交）来提升单次通过率？
3. 人工兜底（截图上人看）与全自动之间，工程上通常怎么取舍？

### P2 出口质量与一致性

- 住宅代理供应商的部分端口近期对目标域名返回 **403**（换端口同样）。
- 机器上另有一条全局隧道，出口是**机房 IP**（非住宅）。
- 观察到：**同一账号若先后使用"住宅 IP"和"机房 IP"，1~2 小时内会被限制。**

**想请评审的问题：**

4. 同一账号的完整生命周期（创建→登录→激活→登记）是否必须绑定**同一出口 IP**？还是只需保证"同国家、同类型"即可？
5. 住宅与机房混用，和"同住宅但不同 IP"，哪个风险更高？
6. 长周期保活（数天到数月）无法固定 IP 时，工程上通常怎么做（固定国家 + 抖动容忍？）

### P3 设备登记的前置条件

- 登记需要一枚**真推送令牌（32 字节）**，本地伪造会被服务端拒绝。
- 目前通过"本机已安装的官方客户端 + 登录一次"取得令牌，链路已通。
- 但这也意味着：**令牌来源依赖客户端状态**，客户端退出后是否失效尚未验证。

**想请评审的问题：**

7. 推送令牌的生命周期怎么判定？失效后能否在同一设备身份下重新获取？
8. 多账号共用同一台机器/同一令牌，是否会造成账号间关联？

## 3. 代码评审请求（重点）

请按下列维度审查整条流水线，指出设计缺陷与更稳妥的做法：

### 3.1 可靠性

- `tools/poolimport`：幂等键设计、超时重放、冲突判定是否完整？
- `tools/capture/create-account.cjs`：重试循环的边界条件、状态判定（靠 DOM 文本判断阶段）是否脆弱？
- `bin/applekeepalive.exe`：失败时是否会破坏已有会话？（当前设计是失败也不覆盖，但请确认）

### 3.2 安全与卫生

- 凭据（密码、短信码、会话 cookie、存储值码）在日志、临时文件、命令行参数里的暴露面；
- `state/accounts/*` 的权限与生命周期；
- 是否有"写操作在结果未知时被重放"的风险（删除、登记、导入三类）。

### 3.3 结构

- 六个阶段目前是"一堆脚本 + 若干 CLI"，没有统一状态机。是否需要引入持久化任务表（阶段、尝试次数、下次执行时间、幂等键）？
- 阶段之间靠文件传递（`session.json`、`icloud-web-session.json`），是否需要显式的契约校验（字段、版本、账号绑定）？

### 3.4 可观测

- 目前只有 stdout 日志。失败时缺少"当次请求/响应"的可复现快照；
- 建议的最小观测集是什么？

---

## 4. 已确定的设计约定（评审时可据此判断）

1. 一个账号 = 一个目录（`state/accounts/<id>`），目录内放会话与设备数据；
2. 账号与出口 IP 在完整生命周期内保持一致（P2 结论前，按最严执行）；
3. 写操作超时一律视为"结果未知"，先回读再决定，不自动重放；
4. 资源池（地址台账）只做记录，不承担远端动作；
5. 远端删除动作只有一个执行者。
