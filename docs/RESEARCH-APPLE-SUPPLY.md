# 研究文档：自建 Apple ID 供给链路

日期：2026-11-15。范围：`appleservices-family-private`（Apple 产线）+ `outlook-workbench`（邮箱供给）。
本文是技术研究文档，重点在**目标是否成立**，其次才是实现。

---

## 一、研究对象

一条**从零到可用**的账号供给链路：

```
邮箱（自有）→ Apple ID 注册 → 激活（条款/会话）→ 设备登记 → 保活
                                    ↓
                          交付给邮箱台（8788）创建 HME 地址
                                    ↓
                          供下游（权益工作台）注册使用
```

**研究对象不是"某个脚本"，而是"这条链路能不能稳定产出可用账号"这个命题。**

---

## 二、研究目标与目标逻辑审查

### 2.1 目标陈述

> 以自有邮箱与自有运行环境，稳定产出可长期使用的 Apple ID，替代对第三方账号供给的依赖。

### 2.2 目标逻辑分解

目标要成立，必须同时满足四个子命题：

| # | 子命题 | 当前证据 | 判定 |
| --- | --- | --- | --- |
| P1 | **能建出账号** | 已建成过（QQ 邮箱 + 英国号 + 住宅出口） | ✅ 成立 |
| P2 | **建出的账号能活到可用** | 有账号 2 小时内被锁；有账号建完即被判异常；无长周期样本 | ❌ **未证明** |
| P3 | **能拿到会话与令牌** | GSA 登录撞限流；网页会话 CLI 未接通；Outlook 侧授权已通（6 秒） | ⚠️ 部分成立 |
| P4 | **邮箱供给可持续** | 自建 Outlook 卡在平台判定；买号有失效风险 | ⚠️ 部分成立 |

### 2.3 目标逻辑的致命问题

**P2 是整条链路的根基，而它恰好是唯一没有数据的。**

```
建号成功 ≠ 账号可用
我们的观测：
  · 一个账号建完后 2 小时内被锁定（HTTP 403）
  · 多个账号提交后即被判"异常活动"
  · 没有任何一个账号活过 24 小时并被验证可用
```

因此当前目标的真实表述应该是：

> **在未知存活率的前提下，尝试产出账号**

而不是"稳定产出"。

**如果 P2 的存活率低于某个阈值（例如 <30%），那么自建链路在成本上不成立**——
因为下游（HME 创建、GPT 注册）要求账号可用，不可用的账号是纯沉没成本。

### 2.4 由此得出的前置实验（本研究的第一个必做项）

```
实验 E1：账号存活率测量
  · 同一环境建 N=10 个账号，不做任何激进操作
  · 分别在 T+1h / T+6h / T+24h / T+72h 检查：能否登录、能否取 webservices
  · 产出：存活曲线 + 半衰期
  · 若 T+24h 存活率 < 30% → 目标需重定义（改为"大量生产 + 快速消费"或放弃自建）
```

**这个实验不做，后面所有优化都是在优化一个可能不成立的目标。**

## 三、研究方法与技术路线

### 3.1 研究方法

```
假设驱动 + 单变量对照 + 证据留存
· 每次只改一个变量（浏览器栈 / 出口 / 语言 / 节奏）
· 失败必须留证据（截图 + run.jsonl + 页面原文）
· 结论只用可复现的数据支撑，不靠推测
```

### 3.2 技术路线（两条并行）

**路线 A：协议优先**
```
GSA 登录 / 条款 / 设备登记 / 保活 —— 全部协议
优点：快、可并发、无浏览器开销
限制：建号这一步协议做不了（页面内工作量证明 + 指纹）
```

**路线 B：浏览器兜底**
```
建号 + 图像验证码 + 交互式校验 —— 浏览器
优点：唯一可行路径
限制：慢、吃资源、被判定面大
```

**现状：A 用于"建号之后"，B 用于"建号本身"。**

### 3.3 已验证的关键技术结论

| 结论 | 证据 |
| --- | --- |
| 环境一致性 > 技术手段 | 本机家宽 + 本地语言能过表单；换任何商业住宅代理即被判 |
| 交互式校验要"跟着控件反馈" | 后台窗口 rAF 被节流 → 按住无反应；前台 1.15 秒通过 |
| 拟人节奏是硬门槛 | 10 秒填完 vs 90 秒填完，结果不同 |
| 邮箱域名差异巨大 | qq/hotmail 放行；outlook.com 被硬拒；icloud 不能作 Apple ID |
| 更换浏览器栈无效 | patchright + 20 国 + 住宅代理，判词不变 |

```
③ 邮箱供给与 Apple 产线尚未联通（取码两套）
```

## 五、后续优化计划

### 阶段 0：先证伪或证实目标（1~2 天，成本 ≈ $0.5）

```
E1 账号存活率测量（见 2.4）
E2 邮箱可用性测量：新 Outlook 号在 T+24h 能否收外部信
→ 两个实验决定后面是否继续投入
```

### 阶段 1：补齐链路断点（3~5 天）

```
① 修 applelogin 的 2FA 选号段（这是"账号→会话"的最后一公里）
② 把两层取码统一（Apple 侧也走 8788）
③ 去掉 Python 中间层，Go 直接调 Node
```

### 阶段 2：工程化（1~2 周）

```
① 任务表 + 断点续跑 + 失败分类
② 并发（受出口与内存约束）
③ 观测面板（成功率、耗时分布、失败归因）
```

### 阶段 3：产能决策（数据驱动）

```
若 E1 存活率 ≥ 30%：自建为主，买号为辅
若 10%~30%：自建仅作补充，主力买号
若 < 10%：放弃自建邮箱与 Apple 号，转为纯消费方
```

## 六、结论

1. **实现层：路线是通的**——建号、取码、授权、协议登录都有可用实现，缺的是"连接处"（2FA 选号、取码统一）。
2. **目标层：尚不成立**——"稳定产出可用账号"中的"可用"没有任何长周期证据，而这是整条链路的价值前提。
3. **因此下一步不是继续优化代码，而是先做 E1/E2 两个测量实验**，用数据决定这个目标值不值得继续投入。

> 如果目标逻辑不成立，实现再漂亮也是零。本研究的优先级：**先证伪目标，再优化实现。**
