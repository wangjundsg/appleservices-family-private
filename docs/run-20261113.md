## 四、本次暴露的问题

### 1. `proxyselect` 硬依赖 `profile.json`，文档步骤顺序跑不通

- **现象**：按「先选代理（步骤 1）→ 再生成指纹（步骤 4）」执行，第一步就 `error=config "no frozen profile in .cache/run-live"`，exit 1。
- **触发条件**：新账号目录（无 `profile.json`）+ 非 `-dry-run`。
- **怀疑原因**：`main.go:131-137` 把「指纹已冻结」当成预检前置（为了把 pick 写进 profile），但流水线文档把指纹排在后面。
- **建议**：`proxyselect` 在缺 profile 时自动调用 profilegen（或退化为 `-dry-run` 只打印 pick 并提示下一步），或把文档顺序改成「profilegen → proxyselect」并在两处交叉引用。

### 2. 预检用非浏览器 UA 探业务页，得到「住宅代理全线 403」的假阳性

- **现象**：dataimpulse 五个出口全部 `status=403`；同一出口换 Chrome UA 立刻 200。
- **触发条件**：`-preflight-url https://account.apple.com/account` + 探针固定 UA `appleservices-proxypool/1`。
- **怀疑原因**：苹果边缘按 UA/客户端指纹拦截非浏览器请求（403）；本机 Clash 与直连也分别被 503/403，说明「403 就是出口被封」这个判定不成立。
- **建议**：探针加真实浏览器 UA/头部（或直接复用 profile 的 UA/CH）；把「403」和「503」分开处理（503 更像边缘风控/临时封锁，不是烧号）；预检目标默认用中性 IP 回显，业务可用性放到建号阶段判。

### 3. `--captcha-cmd` 语义与文档命令不符，16 次空转

- **现象**：`ocr-answer ... length=0` ×16，stderr `python: can't open file '...python tools\captcha\solver.py --provider yes --skip-local'`。
- **触发条件**：按文档把「解释器 + 脚本 + 参数」整串传给 `--captcha-cmd`。
- **怀疑原因**：`create-account.cjs:673` 用 `execFileSync("python", [ocrCmd, png])`，`ocrCmd` 只占一个 argv 位，不会按空格拆分。
- **建议**：`--captcha-cmd` 改为接收 JSON 数组或允许 `--captcha-arg` 重复传入；文档示例改成 `--captcha-cmd "tools\captcha\solver.py"`（provider 默认 yes、key 走 `YESCAPTCHA_KEY`），并在启动时校验脚本文件存在，缺失直接 usage 退出（exit 2）而不是烧 16 轮。

### 4. 验证码图定位按尺寸猜，抓到隐私插画；真实验证码图 503 时无兜底

- **现象**：16 张 `captcha-*.png` 字节完全一致（sha256 `c0184710…`），内容是「两个人握手」插画；`01-submit-*.png` 里验证码位是碎图。
- **触发条件**：挑战页真实验证码 `<img>` 因 `/captcha` 503 未加载（`naturalWidth=0`）+ `captchaImage()` 只按 `naturalWidth>0 && ≤200×120` 取第一张。
- **怀疑原因**：选图靠尺寸启发式，没有 DOM 归属约束；OCR 对插画也能「读出」5 字符，于是失败被伪装成「答案不对」，16 轮全烧在错误对象上。
- **建议**：优先取 `input[name="captcha"]` 邻近的 `img` / `[id*="captcha"] img`；截图前断言 `naturalWidth≥80 && naturalHeight≥30`，否则直接判定「验证码资源不可用」并 fail-fast（不进入 OCR 循环）；同一图连续 2 次哈希相同即中止。

### 5. 出口对苹果 idmsa 资源 503，链路在风控层就被挡住

- **现象**：`/captcha` 31 次全 503、`/account/validation/appleid` 16 次全 503；控制台 `Type the characters in the image` 但图不显示。
- **触发条件**：DataImpulse US 住宅出口 `216.75.151.186`（端口 10005）访问 `idmsa.apple.com` 的挑战/校验接口。
- **怀疑原因**：该出口段被苹果 CDN/风控标黑（503 而非 403，典型的边缘策略拒绝）；本机直连/IPv6 与 Clash 同样被挡，说明当前网络环境整体不适合这条链路。
- **建议**：建号前加一步「idmsa 资源可用性预检」（拉一次 `/captcha` 期望 200/302，503 直接换出口，不进表单）；同时记录每次出口的 503 率做出口池淘汰；必要时换供应商/地区或改用移动网络出口。

### 6. 挑战页首次提交即出现，产物里无法判断表单是否真的提交成功

- **现象**：`01-submit-1.txt` 已是 `Security Challenge Error`，邮箱/密码/电话输入框全部消失；`/account/validate` 只有 400、无 200。
- **触发条件**：首次点击 Continue 后。
- **怀疑原因**：苹果把「注册表单 + 人机验证」合并成挑战页；脚本没有保存提交前的 DOM 快照与表单值校验结果，无法区分「表单校验失败」与「风控直接拦」。
- **建议**：提交前落一份 `pre-submit.html` 与字段非空断言；`/account/validate` 非 2xx 时把响应体状态码写进 run.jsonl；挑战页出现时记录 `/captcha` 的状态码，作为「环境不可用」与「答案错误」的判据。

### 7. 失败不自动退号，$0.13 会挂在账上

- **现象**：`create-account` exit 1 后号码仍 `STATUS_WAIT_CODE`，需人工 `setStatus&status=8` 才退款（本次已退，余额回到 3.9309）。
- **触发条件**：建号在「未请求短信」阶段失败（验证码/表单阶段）。
- **怀疑原因**：脚本只负责建号，不负责号码生命周期。
- **建议**：`create-account` 在 `final.state=failed` 且号码未被使用时自动 `setStatus=8`（或输出一行待执行的取消命令），并在 `run.jsonl` 记 `refund=requested`。

### 8. 空转成本与计时口径缺失

- **现象**：第 1 次建号 76.3s 全在错误 captcha-cmd 上空转；第 2 次 359.6s、16 次付费解算，全部无效；文档没有阶段耗时字段。
- **触发条件**：参数错误 + 验证码对象错误。
- **怀疑原因**：脚本对「解算器连续失败」「同一图重复」没有熔断；`run.jsonl` 只在 `final` 记总耗时。
- **建议**：加熔断（连续 3 次同图/同答案即 fail-fast）；每个 `step` 记 `elapsed_ms`；失败时输出 `captcha_spend` 估算，便于预算复盘。

## 九、补充取证（同日稍后，结论有修正）

### 9.1 新增工具：浏览器探针

`tools/capture/preflight-browser.cjs`：用 Playwright + 同一代理打开注册页，点进表单步骤，
读验证码 `<img>` 的真实尺寸。用它替代原先的 Node 裸 HTTP 探针。

实测（`--click-create`）：

| 出口 | 结果 | 耗时 | 关键数据 |
| --- | --- | --- | --- |
| 本机 TUN（直连） | ok | 21.7s | captcha 160×70，near=1 |
| DataImpulse 10005 | ok | 33.3s | captcha 160×70，near=1 |

**两条出口都能加载验证码**，此前"住宅代理全线被封"的判断不成立。

### 9.2 根因：选图规则把插画当成了验证码

同一次探测里，页面上有两个图满足旧规则"宽≤200 且 高≤120"：

| 元素 | 尺寸 | alt | 距输入框 |
| --- | --- | --- | --- |
| 真验证码 | 160×70 | 安全提示图片 | 1 px |
| 隐私插画 | 124×118 | Privacy Icon | 144 px |

插画在 DOM 里排在前面，旧代码按"第一个尺寸合格"取图，于是**每次都截到插画**。
16 张截图 sha256 完全相同（`c0184710…`）就是这个原因；送进识别服务的也是插画，必然被拒。

修正：改为优先取 `input[name="captcha"]` 邻近的 `img`，并断言 `naturalWidth>0`
（commit `e6118a9`）。

### 9.3 Node 探针的 403 与浏览器 200 并不矛盾

同一出口、同一 URL：

- Node 裸 TLS 探针：`POST /captcha` → 403
- 真实 Chrome：验证码图片正常加载

差异来自 TLS/HTTP2 指纹（Node-OpenSSL vs Chrome BoringSSL），不是 IP 被封。
因此"用裸 HTTP 探针判断出口可用性"这个设计被废弃，门槛改为浏览器探针。

### 9.4 那次 31 次 503 不可复现

同出口、同浏览器、同页面，本次探测正常。无法回溯证明当时是限流还是别的，
按"未复现、存疑"记录，不据此下结论。

### 9.5 教训

1. 判据必须和被测对象同栈：用浏览器测浏览器，用协议测协议。
2. 图元选择不能只靠尺寸，要看 DOM 归属关系。
3. 失败必须先落证据（截图哈希、HTTP 状态序列），否则只能靠回忆推理。
