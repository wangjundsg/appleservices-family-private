### 1.4 根因：`phoneCode` 被 widget 的「晚到水合」重置回 US

一个**有效英国手机号**被判「Enter a valid phone number」，只有两种可能：号码真无效，或表单根本没按 +44 校验。
三个探针把后者钉死了（探针都在 `.cache/r4-1/`，走同一出口 10051）：

**探针 1（`probe-phone.cjs`）**：填完表单 → `selectOption('select[name="phoneCode"]','GB')` → 1.2s 后读回。

```
before  select_value="US"  select_text="+1 (United States)"  phone_value="7541426169"
```

**探针 2（`probe-phone3.cjs`，时间序列）**：

```
after-fill           select=US  +1 (United States)   tel=""
select-GB-0ms        select=GB  +44 (United Kingdom) tel=""
select-GB-400ms      select=GB  +44 (United Kingdom) tel=""
select-GB-2000ms     select=GB  +44 (United Kingdom) tel=""
select-GB-5000ms     select=US  +1 (United States)   tel=""        ← 自己弹回去了
typed-0ms            select=US  tel="(754) 142-6169"              ← 被当成美国号格式化
human-typed-0ms      select=GB  tel="7541426169"                  ← 水合之后重新选就稳
human-typed-1500ms   select=GB  tel="7541426169"
```

结论：表单绘制后 **4~6 秒有一次自身水合**（`/captcha` 201 之后、`phoneCode` 下拉 245 项重排），
那次重渲染把 `phoneCode` 复位成默认 `US`。驱动是「填表 → 等图 → OCR（5~7s）→ 填验证码 → 提交」，
提交时早就过了水合点，于是 `7541426169` 被当成 `+1 754-142-6169` 校验——
美国 NXX 不能以 1 开头（`142`），客户端直接判非法，**表单根本不发**（`/account/validate` 400 是表单级联校验，不是号码被苹果拒）。

**探针 3（`probe-phone4.cjs`，验证修法）**：水合之后重新选国家码 + 重新填号码，再提交（验证码故意填错）：

```
settled 7000ms
after-fill         cc=GB tel="7541426169" phoneError=false
re-asserted        cc=GB tel="7541426169" phoneError=false
after-submit       cc=US tel="7541426169" phoneError=false
validate bodies: [{"status":400,"body":"{ \"validationErrors\" : [ {
  \"code\" : \"captchaAnswer.Invalid\",
  \"message\" : \"Please enter the characters you see or hear to continue.\",
  \"path\" : \"captcha.answer\" } ] }"}]
```

提交真的发出去了，服务端**只**抱怨验证码（`captchaAnswer.Invalid`），**没有任何 phoneNumber 错误** →
修法成立：**表单水合后（≈7s）再填，并在每次点 Continue 前重写一次 国家码+号码**。

## 六、三个根因与修法（本轮全部定位在工具侧）

### 6.1 `phoneCode` 被水合重置（尝试 1 的直接死因，已修已验）

- 现象：`selectOption('select[name="phoneCode"]','GB')` 成功后 4~6 秒被 widget 自己改回 `US`；
  号码被按 `+1` 格式化并判非法 → 客户端拦截，`/account/validate` 400，表单永不提交。
- 修法（三处，本轮落在 `.cache/r4-*/create-account-cc.cjs` 本地副本，未入库）：
  1. `note("step",{at:"form"})` 之后 `sleep(--form-settle, 默认 7000ms)`，等水合过去；
  2. 把「国家码 + 号码」抽成 `fillPhone()`，填表时调一次；
  3. **每次点 Continue 之前再调一次**，落 `phone-cc` 断点（`select` + `tel_digits`）留证。
- 验证：`probe-phone4.cjs` 提交后 400 体里只有 `captchaAnswer.Invalid`；尝试 3/4 的 `/account/validate` 直接 200。

### 6.2 手机步文案带冒号，分类器不认（尝试 3 的直接死因，已修）

- `account-flow.cjs:214`：`PHONE_DELIVERY` 里 `sent to \+?\d` 不允许冒号；实屏是 `sent to: +33 6 05 …`。
- 结果：`classifyScreen` 返回 `unknown`，驱动按「不确定」记账并退出（exit 3），一屏就收口。
- 修法：本地副本新增 `classify()`，**只**把 `unknown` 且匹配 `verify (?:your )?phone number|verification code sent to:?\s*\+?[\d(]` 的屏放宽成 `phone_step`。
- 建议入库版本：把该正则改成 `sent to:?\s*\+?\d`，并为 `Your account cannot be created at this time.` 加一个显式状态（见 §8）。

### 6.3 `Security Code Error` 要图却没有图（尝试 4 的死因，未解）

- 8 屏全部只有红字、没有 `<img>`；驱动的 `input[name="captcha"]` 计数为 0，所以既不进 `inline-captcha` 分支，也无图可解。
- 三处可疑：AuthKit 手机步的验证码资源单独走一次 `/captcha`（本轮 `run.jsonl` 里手机步期间**没有任何** `/captcha` 记录）、
  或该请求被住宅出口丢掉、或苹果对这类号码直接不给图（软拒绝的一种表现）。
- 下一步该做的观测：在手机步期间监听 `**/captcha*` 与 `response` 状态码，并把 widget iframe 的 `frame.url()` 打点，
  才能分清「图没请求」还是「请求了没回」。

## 八、结论与下一步

**结论：4 次尝试、0 账号；但链路首次推进到「短信码被苹果接收 → 苹果回错」这一段，且三个卡点全部定位在工具侧。**

按优先级：

1. **入库两个已验证的修法**（§6.1 水合等待 + 提交前回写国家码；§6.2 手机步分类正则）。这两条是本轮唯一「已实测通过」的成果，
   目前只存在于 `.cache/r4-*/create-account-cc.cjs` 本地副本，仓库里还是旧行为。
2. **补 `Your account cannot be created at this time.` 状态**：这不是 `phone_step`，也不是 `unknown`——它意味着这一号码已被苹果拉黑，
   应直接收口为 `refused`（exit 4 语义）并立刻退号换下一个国家，而不是继续重填短信码烧 8 屏。
3. **观测手机步的验证码资源**（§6.3）：监听 `/captcha` 与 iframe `frame.url()`，先分清「苹果没给图」和「给了没收到」。
   若是后者（出口丢包），换口即可；若是前者（软拒绝），那这条路在虚拟号上就是死胡同，得换号码来源。
4. **不要再用虚拟号硬撞这条闸门**：尝试 3/4 的号码都已被苹果发出短信并标记（hero 侧 `OTP_RECEIVED`、不可退），
   同一段号码重复使用只会更快触发软拒绝。
5. 若仍要跑第五轮：`--form-settle` 保持 7000、preflight 连过两次再买号、失败立即 `setStatus=8`（120s 内别急着退，会 `EARLY_CANCEL_DENIED`）。
